1

3 · Your live layer — named once, renamed never

The layer already carries its themes column with the five kinds. No data changes; the key simply gets its reader-facing name set once, in the layer’s edit screen — the same slot the wizard fills for new keys.

Why not rename the stored column instead? The column name is written into the layer’s data and the manifest’s popup list; renaming it means rewriting a live layer’s rows for a cosmetic gain, and every future reading would still write its own machine name. A name slot does the same job for nothing, everywhere, including the two older Bengaluru test layers that carry theme columns from earlier eras.

Measured (from the live code): the door today — owner.js:448 and databench.js:88 say “Find themes”, with the note “We read your data with AI to find the patterns running through it, and show them as themes.” The hardcoded column — owner.js:1197 (o.themes = …), databench.js:801 (ensureColumn("themes")), and the server’s reading may only answer “themes” (api/lib/atlas/enrich.js:162). The switch label — atlas.js:1104–1106 lowercases the raw column name (prettyCol), applied at atlas.js:1186, rendered at atlas.js:1577; no manifest slot overrides it anywhere in atlas.js. The popup label — api/lib/fragment.js:390 capitalises the same name (prettify), stored per layer as { "label": "Themes", "property": "themes" }. The five patterns and counts (25/22/8/7/4 of 66) are the approved wizard drawing’s own. The word “patterns” appears in no reader-facing code today.

Reasoned (design intent, not code): the name slot in the manifest and the switch reading it; the reading suggesting a name (“Kinds of place” here is an example, one more string from the same paid call); “show the stored name as it is” replacing both prettifiers.
